# 阶段 6 · 交付给开发：规格说明书

规格说明书的目标不是"写得全"，而是"开发看完不用回来问"。每条需求必须可验收：有输入、有预期表现、有边界条件、有验收方式。

## 一、文档结构（固定七章）

1. **项目概述**：一句话玩法、目标用户、平台与形态、上线目标时间。
2. **核心循环**：循环图、单局流程、结算规则、数值表。
3. **功能清单**：模块 × 功能 × 优先级（P0 必做 / P1 应做 / P2 可选）。
4. **界面与交互**：页面清单、状态机、跳转关系、异常态（空/加载/失败/断网）。
5. **数据与存档**：本地存档字段、云存档策略、字段类型与默认值。
6. **广告与支付**：触发点、频次上限、失败兜底、开关配置。
7. **验收标准**：可执行的检查项，逐条可勾。

## 二、功能条目写法（对照）

❌ 不可验收：
> 实现排行榜功能，体验流畅。

✅ 可验收：
> **好友排行榜（P0）**
> - 入口：主界面右上图标，点击进入。
> - 数据：读取开放数据域内好友最高分，按分数降序，同分按时间升序。
> - 展示：前 50 名，滚动加载；自己不在前 50 时底部固定显示自己排名。
> - 空态：无好友数据时显示"暂无好友上榜"，并提供邀请入口。
> - 异常：开放数据域加载失败 → 显示上次缓存 + 重试按钮。
> - 验收：好友 ≥ 3 人时，排名与分数一致；断网时页面不白屏。

## 三、状态机与异常态

每个核心页面画出状态：`初始 → 加载中 → 成功 / 空 / 失败`。四态齐全才算设计完，只画"成功态"是新手最常见的问题。

| 态 | 必须设计的内容 |
|---|---|
| 加载中 | 进度反馈（超过 1s 必须有） |
| 空态 | 说明文案 + 引导动作 |
| 失败态 | 原因 + 重试 + 降级路径 |
| 边界态 | 资源上限、满级、次数用尽 |

## 四、数值表交付格式

用 CSV/表格而不是正文描述，程序可直接读取：

```csv
level,mechanism,timeLimit,obstacleDensity,maxMistake,rewardCoin,rewardItem
1,jump,60,low,3,50,
2,jump,60,low,3,55,
3,jump+flip,50,mid,2,80,skin_fragment
```

## 五、接口契约（策划侧只需定义"要什么"，不定义"怎么写"）

| 能力 | 输入 | 输出 | 失败处理 |
|---|---|---|---|
| 广告激励视频 | 广告位 ID、场景标识 | 是否看完（bool） | 加载失败 → 直接发奖 |
| 支付下单 | 商品 ID、数量 | 订单结果 | 超时 → 提示重试，不重复扣 |
| 排行榜读取 | 排序维度 | 列表（名次/昵称/分数） | 失败 → 缓存兜底 |
| 存档同步 | 存档对象 | 成功/冲突 | 冲突 → 取较新，保留备份 |

明确写出"策划不决定实现方式"，避免越界指导工程。

## 六、验收标准模板

```markdown
## 验收清单：<模块名>
[ ] 主流程可完成，无阻断
[ ] 四态齐全（加载/成功/空/失败）
[ ] 按钮热区 ≥ 44×44，边缘留白 ≥ 16px
[ ] 弱网（3G/丢包 20%）下不崩、不白屏
[ ] 低端机帧率不低于 <阈值>
[ ] 广告加载失败有兜底
[ ] 存档读写在杀进程后不丢失
[ ] 无调试入口与测试数据
```

## 七、变更管理

- 需求变更必须记录：变更内容、原因、影响范围（工期/包体/其他模块）、确认人。
- 提审前两周冻结 P0 范围，只修 Bug 不加功能。
- 包体每次合入后回归检查是否超限（限额以平台最新文档为准）。

## 八、交接检查

交付前问自己四个问题：
1. 开发能不能只靠这份文档做出 P0 版本？
2. 每个"做完"的判断标准是否可被第三方验证？
3. 异常情况是否都写了处理方式？
4. 有没有把实现细节（框架、写法）写进策划文档？（有则删除）
